# ORE Experiment Workbench

I recommend building this as a standalone, reusable testing application inside your existing `wizekin/ORE-Neurocomputational` repository.

The central idea is to make ORE behave like an experimental reasoning system that you can interrogate through a conversational interface.

<AsyncImage query="modern dark scientific AI research dashboard chat interface neural network experiment laboratory software UI" aspectRatio="16:9" width="100%"/>

## 1. Proposed interface

The application will be called **ORE Experiment Workbench**.

It will have three main areas:

- **Left sidebar:** Select the ORE component to experiment with.
- **Central chat:** Enter prompts and receive responses produced by the selected Python implementation.
- **Right-side inspector:** Examine execution traces, intermediate representations, mathematical operations, outputs, and errors.

The 13 selectable components will be:

| Component group | Components |
|---|---|
| Infrastructure | `ore_contracts` |

Each component must be independently testable, without requiring the entire ORE pipeline to execute.

## 3. How it works technically

I added live instrumentation to `observer.py`.

It uses Python's profiling and tracing mechanisms, with a separate worker thread and a thread-safe event queue communicating with Streamlit.

Importantly, it doesn't require rewriting all 13 ORE components to make basic function-level debugging possible.

The debugger also preserves the existing observations:

- Numerical array statistics.
- Component-generated operation traces.
- Validation results.
- Function execution durations.
- Final output and traceback.

One limitation: Python function activity is visible live, but named algorithm-stage records are displayed after a component returns unless that component explicitly emits progress events. NumPy/SciPy internal C-level instructions are not individually visible.

I’ve implemented the new **ORE Execution Observatory** in `wizekin/ORE-Neurocomputational`.

The main architectural decision is to keep explanations outside the Python source files, as you requested. Instead of embedding large English annotations above every function, ORE maintains a central SQLite catalogue and looks up the explanation associated with each function or class when it executes.

## 1. Repository-wide annotation catalogue

I inventoried the repository's 111 Python files and implemented an AST-based scanner that indexes:

- Python modules and package entry points.
- Classes and their methods.
- Nested functions.
- Ordinary and asynchronous functions.

For each definition, the catalogue stores its qualified name, source file, line range, signature and plain-English explanation.

There are two sources for the explanations:

**Existing documentation:** Where a class or function already has a docstring, the catalogue uses it.

**Generated explanations:** Where no docstring exists, the scanner constructs an initial explanation using the function name, arguments, return type, helper calls and control-flow structure. These entries are identified as source-generated rather than manually verified.

You can improve these explanations directly in the viewer. Manual edits are retained when the catalogue is refreshed, and an annotation is marked for review when its own source code changes.

## 3. Automatic logging whenever Python runs

The repository now includes a Python startup hook.

After installation, launching a Python script inside the repository automatically creates a new run record. You do not need to modify the script or call a logging function manually.

For each run, the logger captures:

- Date and time, in local time and UTC.
- A unique execution ID.
- Python function and method calls and returns.
- Class entry events.
- Exceptions and their locations.
- Function durations and execution order.
- Links to the explanations stored in SQLite.

It also supports running package entry points using `python -m`.
