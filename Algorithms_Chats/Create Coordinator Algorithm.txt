**Priority:** 3

**Objective:** Build a central coordination system that allows ORE's specialized cognitive networks and individual structures to cooperate to solve complex cognitive tasks.

**Proposed implementation:** Extend `ore_contracts.CanonicalOREController` with a dependency-aware cognitive task execution system, while preserving the existing N9 processor and shared workspace architecture.

# 3. Detailed implementation algorithm

I divide the algorithm into 12 major phases.

## Phase 1 — Initialize the brain coordinator

**Purpose:** Initialize the global coordination environment without modifying existing specialist implementations.

### Algorithmic steps

1. Initialize `CanonicalOREController`.
2. Initialize or retrieve its existing `CanonicalBackendRegistry`.
3. Initialize `ModuleRegistry` connected to the existing `ContractCatalog`.
4. Register existing contracts using `register_existing_contracts()`.
5. Initialize the shared workspace manager.
6. Initialize an artifact storage mechanism for typed `ContractArtifact` objects.
7. Initialize the bounded execution scheduler.
8. Initialize the execution logger.
9. Construct a unique task execution context.

Proposed new module:

`ore_contracts/coordinator.py`

Proposed classes:

The global controller should expose a new method:

This method delegates the actual task planning and execution to `CognitiveTaskCoordinator`.

The existing `CanonicalOREController.run()` must remain backward compatible.

### Mathematical operations

Assign each execution a unique identifier.

Generate reproducible input fingerprints:

\[
H_{input} = SHA256(\operatorname{CanonicalJSON}(input))
\]

Use the fingerprint to identify identical inputs and avoid accidentally executing the same operation twice.

Create an execution context containing:

- Run ID.
- Operation mode.
- Random seed.
- Compute budget.
- Per-module timeout limits.
- Model references.
- Execution settings.

Reuse the existing `RunContext` and `ComputeBudget` classes.

## Phase 2 — Receive and understand the cognitive task

**Purpose:** Transform an incoming request into an explicit computational objective.

The coordinator receives a `CognitiveTask`.

Proposed data structure:

For example, imagine that ORE receives:

> Understand this sentence, identify its meaning, compare it with relevant stored knowledge, and determine whether its meaning is consistent with previous information.

The task should be decomposed into requirements:

| Requirement | Required capability |
|---|---|
| Recognize the input | Language recognition |
| Maintain intermediate information | Working memory |
| Retrieve relevant concepts | Semantic memory |
| Interpret the meaning | Semantic composition |
| Evaluate surrounding information | Contextual reasoning |
| Check inconsistencies | Conflict detection |

These capability identifiers are examples of proposed manifest entries, not claims that all corresponding capabilities are already registered.

### Mathematical operations

Represent the task as a vector of requirements:

\[
T = [r_1,r_2,\ldots,r_n]
\]

Each \(r_i\) represents a required cognitive operation.

A task can also contain optional operations:

\[
T = T_{\text{required}} \cup T_{\text{optional}}
\]

**Important:** Initially, the decomposition should rely on explicit task requirements and deterministic routing rules. A general-purpose cognitive task interpreter can be developed later rather than assuming the current system already has one.

## Phase 3 — Identify suitable cognitive modules

**Purpose:** Find which modules can contribute to the task.

Use the existing `ModuleRegistry`.

For each required capability:

1. Query `find_by_capability()`.
2. Retrieve the corresponding module manifests.
3. Identify all modules declaring that capability.
4. Retrieve their module identities and versions.
5. Identify their declared input and output ports.
6. Identify their dependencies.
7. Distinguish modules that are registered from modules that actually have executable backends.

Example:

The important distinction is between:

- A module that exists.
- A module that has been registered.
- A module that has an executable backend.
- A module whose backend has been validated.
- A module that is actually available to execute.

The repository already distinguishes several of these states through `CapabilityRecord`.

### Mathematical operations

Calculate capability coverage:

\[
C_{\text{coverage}} =
\frac{\text{number of matched required capabilities}}
{\text{total required capabilities}}
\]

For selecting between multiple providers of the same capability, introduce a ranking score:

\[
S_i =
\alpha R_i +
\beta Q_i +
\gamma D_i -
\lambda L_i
\]

Where:

- \(R_i\): relevance to the current task.
- \(Q_i\): observed module reliability.
- \(D_i\): dependency readiness.
- \(L_i\): resource consumption or current load.
- \(\alpha,\beta,\gamma,\lambda\): configurable weights.

These scores should be based on actual measured information. Unknown availability or reliability must not be replaced with invented values.

## Phase 4 — Inspect the information required by each module

**Purpose:** Determine exactly what information each selected structure needs before execution.

This phase is particularly important because two cognitive structures may require completely different representations of the same information.

For every selected module:

1. Retrieve its `ModuleManifest`.
2. Inspect its `input_ports`.
3. Identify required and optional inputs.
4. Identify the expected contract IDs.
5. Identify accepted contract versions.
6. Identify whether multiple artifacts are accepted.
7. Identify validation requirements.
8. Identify dependencies on other modules.
9. Search the shared workspace and artifact ledger for compatible information.

For example:

| Module | Required information |
|---|---|
| Working memory | Current task, relevant intermediate findings |
| Semantic memory | Concept or semantic retrieval query |
| Contextual reasoning | Semantic hypotheses and discourse context |
| Learning and feedback | Prediction errors and verified feedback |
| N9 | Valid `N9Request` and its localized input patches |

The coordinator should construct an input plan for each module.

Example:

The exact module identifier is illustrative.

### Mathematical operations

For each required information item \(x_j\), define:

\[
A_{ij} =
\begin{cases}
1 & \text{if module }i\text{ accepts information }j\\
0 & \text{otherwise}
\end{cases}
\]

This produces an input compatibility matrix:

\[
A =
\begin{bmatrix}
A_{11} & A_{12} & \cdots\\
A_{21} & A_{22} & \cdots\\
\vdots & \vdots & \ddots
\end{bmatrix}
\]

A module can execute only when all its mandatory input requirements are satisfied.

Contract compatibility must use exact registered schema versions. No implicit conversion should occur.

**Additional implementation requirement:** The existing shared workspace stores JSON-compatible findings, while cognitive modules exchange typed `ContractArtifact` objects. Introduce an `ArtifactLedger` to preserve typed artifacts and publish their references, hashes and provenance into the workspace. This provides the missing bridge between the two systems.

## Phase 5 — Construct the dependency graph

<badge color="success">Core algorithm</badge>

**Purpose:** Determine the order in which cognitive structures must execute.

A module should not execute merely because it is available. It should execute when the information it needs has become available.

Represent the selected modules as a directed graph:

\[
G=(V,E)
\]

Where:

- \(V\) = selected cognitive modules.
- \(E\) = dependencies between those modules.

An edge:

\[
M_i \rightarrow M_j
\]

means that module \(M_j\) needs information or successful completion from module \(M_i\).

This is an example execution graph, not a fixed sequence that every task must follow.

### Algorithm

1. Create one graph node per selected module.
2. Add edges from declared required dependencies.
3. Add information-flow edges when one module's output contract satisfies another module's required input port.
4. Automatically include necessary upstream modules that were not initially selected.
5. Validate all mandatory dependencies.
6. Detect circular dependencies.
7. Reject or replan invalid graphs.
8. Calculate execution layers using topological sorting.

Use Kahn's algorithm for topological sorting.

At each iteration:

- Find nodes with zero remaining incoming edges.
- Place them in the current execution layer.
- Remove their outgoing edges.
- Repeat until all nodes are scheduled.

If nodes remain but no node has zero incoming edges, a dependency cycle exists.

### Result

The coordinator obtains execution layers:

\[
L_1,L_2,\ldots,L_k
\]

All independent modules within one layer can potentially execute concurrently.

A module in \(L_{i+1}\) must wait for its required upstream outputs from earlier layers.

One essential distinction: the registry's current dependency diagnostics check backend readiness, not whether a dependency has actually produced successful artifacts in the current task. The new scheduler must enforce both conditions.

## Phase 6 — Schedule execution using priority and resource availability

**Purpose:** Ensure that the appropriate modules execute at the appropriate time without overloading the system.

Not every available module needs to execute immediately.

The coordinator should consider:

- Required versus optional modules.
- Number of downstream modules waiting for their outputs.
- Task urgency.
- Estimated execution time.
- Memory consumption.
- Current worker availability.
- Historical performance.

### Mathematical scheduling score

Define:

\[
P_i =
\alpha R_i+
\beta K_i+
\gamma U_i+
\delta Q_i-
\lambda C_i
\]

Where:

| Variable | Meaning |
|---|---|
| \(R_i\) | Task relevance |
| \(K_i\) | Downstream dependency importance |
| \(U_i\) | Task urgency |
| \(Q_i\) | Historical reliability |
| \(C_i\) | Resource cost and load |

All inputs should be normalized to comparable scales.

### Scheduling algorithm

1. Obtain the current execution layer.
2. Inspect the available worker slots.
3. Calculate the priority of every ready module.
4. Sort modules by priority.
5. Start independent modules concurrently.
6. Assign each module a timeout.
7. Track memory and compute consumption.
8. Collect completed results.
9. Release execution resources.
10. Move to the next dependency layer when its requirements are fulfilled.

Use the existing `ModuleScheduler` for reactive, event-driven activation following workspace updates. The initial dependency-graph execution should remain controlled by the task coordinator because event subscriptions alone do not implement the complete task DAG.

The repository's existing scheduler already supports bounded worker counts, execution timeouts and activation limits.

## Phase 7 — Execute modules and publish their results

**Purpose:** Make information generated by one cognitive structure available to other structures.

Each module must communicate using the existing `OREModuleProtocol`.

The coordinator supplies:

The expected output is a `ModuleResult`.

The result can have one of these statuses:

| Status | Meaning |
|---|---|
| SUCCESS | Completed successfully |
| PARTIAL | Produced incomplete results |
| ABSTAINED | Could not make a supported decision |
| UNAVAILABLE | Could not execute |
| FAILED | Execution failed |

### Output validation

Before accepting outputs:

1. Check module identity and version.
2. Check the output contract IDs.
3. Check the schema versions.
4. Validate each `ContractArtifact` against `ContractCatalog`.
5. Verify provenance.
6. Verify artifact hashes.
7. Check parent artifact references.
8. Check that the outputs belong to declared output ports.

Reject invalid outputs rather than allowing them to contaminate shared cognitive state.

### Publishing into the shared workspace

For every valid result:

1. Store the typed artifact in `ArtifactLedger`.
2. Generate an immutable artifact reference.
3. Construct a workspace `Finding`.
4. Include the producer module identity.
5. Include its provenance and source evidence.
6. Include the base workspace revision.
7. Include accepted upstream finding dependencies.
8. Submit through `SharedWorkspace.publish()`.

The workspace publication system should decide whether the finding is:

- Accepted.
- Merged.
- Conflicting.
- Deferred.
- Rejected.
- Duplicate.

The coordinator must respect these decisions.

**Important:** The existing workspace has field-level write permissions. New specialist modules must receive explicit permissions for their intended workspace fields. They should never modify shared state directly.

For example:

- Working memory publishes to `working_memory`.
- Semantic processing publishes to `semantic_hypotheses`.
- Contextual processing publishes to `discourse_context`.
- Cognitive control publishes to `unresolved_questions` and `module_status`.

An explicit output-to-workspace-field mapping should connect each module's output ports to the appropriate writable fields.

## Phase 8 — Detect missing information

**Purpose:** Identify when a module cannot perform its task because necessary information is missing.

Consider this situation:

The semantic memory module receives a request but cannot find the concept representation required to retrieve related knowledge.

The coordinator must not simply terminate the entire cognitive operation.

### Algorithm

1. Inspect the failed or partial module result.
2. Determine which required input is missing.
3. Identify its contract ID and accepted versions.
4. Search the artifact ledger for compatible artifacts.
5. Search ModuleRegistry for modules that can produce the missing information.
6. Check whether those modules are available.
7. Add suitable producer modules to the execution graph.
8. Recalculate dependencies.
9. Reschedule affected modules.

If no suitable module exists, create a structured unresolved-information request.

For example:

The coordinator can also determine whether missing information must be obtained from the task input rather than computed by another module.

### Mathematical operations

Calculate missing-input coverage:

\[
M_i =
\frac{\text{available required inputs}}
{\text{total required inputs}}
\]

When:

\[
M_i=1
\]

the module has all mandatory inputs.

When:

\[
M_i<1
\]

the coordinator must resolve the missing requirements or explicitly mark the module blocked.

Optional input absence should not automatically block execution.

## Phase 9 — Detect conflicts and request additional processing

<badge color="success">Critical feedback mechanism</badge>

**Purpose:** Allow cognitive structures to challenge and correct each other's results.

Imagine:

- N9 identifies a word as candidate A.
- Semantic memory strongly supports candidate B.
- Contextual reasoning supports candidate B.
- Previous knowledge supports candidate A.

The coordinator must detect the disagreement rather than silently select one result.

### Algorithm

1. Collect all findings associated with the same cognitive question.
2. Match hypotheses using their semantic targets.
3. Identify contradictory findings.
4. Consult workspace conflict records.
5. Preserve both hypotheses and their evidence.
6. Identify which additional processing could resolve the disagreement.
7. Create a new targeted processing task.
8. Schedule only the relevant modules.
9. Compare the new evidence with the existing evidence.
10. Update the decision when sufficient evidence becomes available.

For example, the coordinator may request:

- N9 to reconsider a particular recognition hypothesis.
- Semantic memory to retrieve additional associations.
- Contextual reasoning to reassess sentence-level compatibility.
- Learning and feedback modules to inspect a prediction error.

### Mathematical operations

Suppose the system has \(K\) competing hypotheses with probabilities \(p_1,\ldots,p_K\).

Calculate normalized uncertainty using entropy:

\[
H_N =
\frac{-\sum_{j=1}^{K}p_j\log(p_j+\epsilon)}
{\log K}
\]

For \(K>1\):

- Low entropy indicates that evidence concentrates around a small number of hypotheses.
- High entropy indicates that evidence remains distributed across alternatives.

Calculate disagreement between comparable module scores:

\[
\bar{s} =
\frac{\sum_i w_i s_i}{\sum_i w_i}
\]

\[
D =
\frac{\sum_i w_i(s_i-\bar{s})^2}
{\sum_i w_i}
\]

Here, \(w_i\) represents evidence reliability, calibration and provenance quality.

These calculations are useful only when the module outputs represent comparable quantities. Uncalibrated scores must not be treated as probabilities.

### Prevent infinite feedback

Introduce:

- Maximum processing attempts.
- Maximum execution time.
- Maximum additional modules.
- A minimum improvement threshold.
- A convergence condition.

Stop when one of these conditions is reached:

1. The required evidence is sufficient.
2. Additional processing produces negligible improvement.
3. The task's resource budget is exhausted.
4. The coordinator determines that the available modules cannot resolve the uncertainty.

The existing `ModuleScheduler` can support bounded event-driven feedback.

## Phase 10 — Combine the results

**Purpose:** Construct one integrated cognitive result without losing individual evidence.

The coordinator collects:

- N9 recognition and comprehension results.
- Working-memory contents.
- Retrieved semantic information.
- Contextual interpretation.
- Conflict-resolution results.
- Learning and feedback information, when applicable.

The result should retain the origin of every important conclusion.

For example:

### Evidence integration

The coordinator should distinguish three situations:

**Agreement:** Multiple independent modules support the same hypothesis.

**Complementary evidence:** Different modules supply different pieces of information that collectively satisfy the task.

**Contradiction:** Modules provide incompatible hypotheses.

Agreement should not automatically mean truth. Modules sharing the same upstream evidence must not be counted as independent confirmations.

The result-combination policy should account for:

- Evidence quality.
- Source reliability.
- Calibration.
- Dependency relationships.
- Information completeness.
- Remaining conflicts.

For a task requiring a definitive answer, uncertainty must be retained rather than artificially eliminated.

## Phase 11 — Make the final decision with uncertainty

**Purpose:** Determine whether the cognitive task has actually been completed.

Introduce a final result structure:

Possible decision statuses:

| Status | Meaning |
|---|---|
| RESOLVED | Requirements satisfied and evidence supports a conclusion |
| PARTIAL | Some requirements satisfied |
| AMBIGUOUS | Multiple plausible interpretations remain |
| ABSTAINED | Insufficient evidence for a supported answer |
| BLOCKED | Mandatory module or input unavailable |
| FAILED | Execution could not complete |

Use the existing workspace goal evaluator to assess whether the requested goal has been satisfied.

The final decision should be based on:

\[
\text{Decision} =
f(
\text{Goal Coverage},
\text{Evidence Quality},
\text{Conflicts},
\text{Uncertainty},
\text{Module Status}
)
\]

Do not convert every numerical score into a probability. A numeric confidence should only be returned as calibrated confidence when appropriate calibration evidence exists.

- Dependency graph.

- Module execution times.
- Produced artifacts.

1. Verify all expected dependencies.

# 7. Testing algorithm

Before integrating this coordinator with all existing ORE packages, test the coordination mechanism independently.

| Test | Expected behavior |
|---|---|
| Module discovery | Finds modules declaring required capabilities |
| Missing backend | Marks module unavailable |
| Disabled module | Excludes it from execution |
| Missing input | Prevents premature execution |
| Contract mismatch | Rejects invalid information |
| Dependency ordering | Executes modules in the correct order |
| Independent modules | Executes concurrently |
| Circular dependencies | Detects and rejects cycles |
| Failed upstream module | Blocks dependent operations |
| Partial output | Preserves incomplete status |
| Workspace publication | Uses controlled publication |
| Conflicting findings | Preserves both competing hypotheses |
| Additional processing | Executes targeted reprocessing |
| Infinite feedback | Stops at configured limits |
| N9 integration | Executes existing N9 through its bridge |
| Provenance | Retains the full execution history |
| Uncertainty | Does not invent calibrated confidence |

## 9. What Task 3 will accomplish

After implementation, ORE should have a fundamentally different ability from a collection of independent Python packages.

Consider a task requiring recognition, memory retrieval, reasoning and conflict resolution.

Before Task 3:

- N9 can perform its own processing.
- Working memory can perform its own processing.
- Semantic memory can perform its own processing.
- Other structures can execute their specialized algorithms.

But there is no general task-level mechanism ensuring that they cooperate according to their actual information dependencies.

After Task 3:

- The coordinator determines which structures are necessary.
- Each structure receives the correct information.
- Independent structures can work simultaneously.
- Dependent structures wait for their required inputs.
- Results become available through shared, validated artifacts.
- Conflicts trigger additional processing.
- The coordinator evaluates the combined evidence.
- The final answer preserves its uncertainty and provenance.

**The most important architectural outcome:** ORE gains a mechanism for coordinated cognition rather than simply accumulating more independent cognitive algorithms.

The next implementation target should be **Phase 1 through Phase 5: initialize the coordinator, define cognitive tasks, discover modules, inspect their inputs, and construct the dependency graph.** This creates the foundation upon which actual cooperative execution can be built.
