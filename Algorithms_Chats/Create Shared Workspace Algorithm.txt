# ORE-Neurocomputational — Task 2: Create a Shared Brain Workspace

## 1. Objective

The purpose of Task 2 is to create a **centralized, structured cognitive workspace** through which the disconnected brain-like modules of ORE-Neurocomputational can exchange, access, update, and coordinate information while working on the same input.

The workspace should act like a shared mental state, not like a central intelligence that performs all the reasoning itself.

<text color="success" weight="semibold">The goal is shared information, controlled updates, and coordinated reasoning without turning the workspace into a monolithic brain.</text>

For example, when ORE receives:

> The boy opened the door.

Different modules may independently produce:

- Lexical processing: `boy → PERSON`
- Lexical processing: `opened → ACTION`
- Lexical processing: `door → OBJECT`
- Syntactic processing: `The boy → subject`, `opened → predicate`
- Semantic processing: `PERSON performs ACTION upon OBJECT`
- Working memory: maintains the boy, action and door while processing the sentence
- Memory: retrieves related knowledge about opening doors
- Cognitive control: evaluates whether the interpretations are consistent
- Discourse processing: connects the sentence to previous sentences

These structures need a common place where their findings become accessible to other modules.

### 2.1 The five mechanisms

| Mechanism | Responsibility |
|---|---|
| <text weight="medium" color="#0D9488">Workspace</text> | Stores the current shared cognitive state. |
| <text weight="medium" color="#D97706">State manager</text> | Validates and commits state modifications. |
| <text weight="medium" color="#2563EB">Publication system</text> | Allows modules to submit findings without directly overwriting others. |
| <text weight="medium" color="#9333EA">Event notification</text> | Informs relevant modules that new information is available. |
| <text weight="medium" color="#64748B">ORE logger</text> | Records execution observations, update decisions, errors and performance. |

The workspace must not require all modules to execute simultaneously. It should support asynchronous operation, partial results, competing hypotheses, and modules that are temporarily inactive.

# 3. Algorithm: Shared Cognitive Workspace

<text color="success" weight="semibold">Algorithm SW-01 — Shared Brain Workspace Initialization, Publication and Controlled Integration</text>

### Phase A — Initialize the cognitive workspace

**Step 1. Create a workspace instance**

When a new input arrives, the central coordinator creates a workspace instance associated with that input and its processing session.

The workspace should contain:

<text color="secondary" size="sm">This is an illustrative structure. The actual implementation should use typed models and data structures rather than treating this dictionary as the final implementation.</text>

**Mathematical operation:**

Create a state vector:

\[
\mathbf{W}_t =
\begin{bmatrix}
L_t\\
S_t\\
M_t\\
D_t\\
WM_t\\
R_t\\
Q_t\\
G_t
\end{bmatrix}
\]

Where:

- \(L_t\): lexical information.
- \(S_t\): syntactic information.
- \(M_t\): semantic information.
- \(D_t\): discourse state.
- \(WM_t\): working memory.
- \(R_t\): retrieved memories.
- \(Q_t\): unresolved questions.
- \(G_t\): current processing goal.

<text color="secondary">This is a conceptual state vector. Its elements may be structured objects rather than numerical vectors.</text>

The workspace is initialized with the input and empty or default representations.

---

### Phase B — Define a common information protocol

**Step 2. Define the standard representation of a module finding**

Each module must publish findings using a standardized envelope.

Example:

Every finding must identify:

- <text weight="medium">Producer:</text> Which module produced the result?
- <text weight="medium">Target:</text> Which shared field or cognitive object does it concern?
- <text weight="medium">Payload:</text> What information is being proposed?
- <text weight="medium">Provenance:</text> What evidence and rules generated it?
- <text weight="medium">Confidence:</text> How reliable is the hypothesis, if applicable?
- <text weight="medium">Dependencies:</text> Which earlier findings were used?
- <text weight="medium">Revision:</text> Which version of the workspace was used when the finding was generated?

The protocol allows different modules to communicate even if they have different internal implementations.

**Mathematical operation:**

Confidence can be represented as:

\[
c_i \in [0,1]
\]

For a finding \(F_i\), confidence is a property of that finding, not an automatic measure of truth.

The state manager should preserve the confidence and evidence separately rather than treating confidence as an absolute truth value.

---

### Phase C — Assign workspace ownership

**Step 3. Define write permissions**

The workspace is shared, but the modules do not have unrestricted write access.

| Module | Primary publishing responsibility |
|---|---|
| Lexical processing | Lexical hypotheses, word features and lexical relations |
| Syntax processing | Syntactic structures and grammatical relations |
| Semantic processing | Semantic interpretations and compositional relations |
| Working memory | Memory maintenance, activation, retention and removal proposals |
| Memory retrieval | Retrieved-memory candidates and relevance scores |
| Cognitive control | Conflict evaluations, priority proposals and processing decisions |
| Discourse processing | Discourse context and discourse relations |
| Goal/control system | Goals, subgoals and task transitions |

Each module may read permitted shared information, but it should publish changes through the state manager.

<text color="warning" weight="medium">A module should not directly overwrite another module's findings.</text>

For example, the semantic processor should not erase lexical hypotheses because it disagrees with them. It should submit a semantic interpretation and, if necessary, a conflict report.

---

### Phase D — Establish subscriptions

**Step 4. Register modules as consumers of relevant information**

Each module declares what information it needs.

Example:

The subscription system should be configurable rather than hardcoded permanently.

Each module receives notifications when a field it subscribes to changes.

This prevents every module from being forced to inspect the entire workspace after every update.

**Mathematical operation: selective notification**

Define the subscription matrix:

\[
A_{ij} =
\begin{cases}
1 & \text{if module } i \text{ subscribes to field } j\\
0 & \text{otherwise}
\end{cases}
\]

If field \(j\) changes, only modules with:

\[
A_{ij}=1
\]

are eligible to receive that change notification.

This reduces unnecessary computational work.

---

### Phase E — Publish findings

**Step 5. Allow modules to submit findings independently**

A module begins processing when it receives input, a notification, or a task assignment.

It then:

1. Reads the relevant workspace snapshot.
2. Executes its own algorithm.
3. Produces zero or more findings.
4. Attaches evidence, dependencies and provenance.
5. Submits the findings to the state manager.

For example, the lexical module might publish three findings:

These are proposals, not yet authoritative changes to the workspace.

A module may submit multiple competing hypotheses rather than forcing one interpretation prematurely.

---

### Phase F — Validate incoming findings

**Step 6. Validate each proposed update**

The state manager receives a finding and performs a series of checks.

<box border radius="xl" padding={3} gap={2}>
  <text weight="medium">Validation pipeline</text>
  <box border radius="lg" padding={2} align=center>1. Validate structure and schema</box>
  <icon name="arrow-down" color="secondary"/>
  <box border radius="lg" padding={2} align=center>2. Validate producer permissions</box>
  <icon name="arrow-down" color="secondary"/>
  <box border radius="lg" padding={2} align=center>3. Validate workspace and revision</box>
  <icon name="arrow-down" color="secondary"/>
  <box border radius="lg" padding={2} align=center>4. Validate provenance and dependencies</box>
  <icon name="arrow-down" color="secondary"/>
  <box border radius="lg" padding={2} align=center>5. Validate compatibility and consistency</box>
  <icon name="arrow-down" color="secondary"/>
  <box border radius="lg" padding={2} align=center>6. Accept, reject or defer</box>
</box>

#### 6.1 Schema validation

Check:

- Required fields exist.
- Payload types are correct.
- IDs are valid.
- Confidence values are within valid ranges.
- Referenced workspace exists.

#### 6.2 Authorization validation

Check that the producer is authorized to submit the proposed field.

For example:

- Lexical processor cannot directly modify the discourse context.
- Memory retrieval cannot directly rewrite the current input.
- Cognitive control cannot arbitrarily rewrite lexical evidence.

#### 6.3 Revision validation

Determine whether the finding was generated against a compatible workspace revision.

If the workspace changed after the module read it, the state manager should determine whether the finding remains valid.

#### 6.4 Provenance validation

Verify that the finding has sufficient source information.

The system should distinguish:

- Input-derived evidence.
- Rule-derived evidence.
- Memory-derived evidence.
- Other-module-derived evidence.
- Inference-derived evidence.

#### 6.5 Dependency validation

A finding may depend on other findings.

For example:

\[
F_{\text{semantic}}
\rightarrow
\{F_{\text{lexical}}, F_{\text{syntactic}}\}
\]

If a dependency is missing, the finding may be deferred rather than rejected.

#### 6.6 Consistency validation

Check for incompatible data, duplicate findings, invalid references, or contradictions with accepted state.

<text color="secondary">Consistency checking should not mean automatically rejecting any contradictory hypothesis. Cognitive systems must be capable of maintaining unresolved conflicts.</text>

### Phase G — Commit accepted changes

**Step 7. Commit changes through the state manager**

After validation, the state manager decides how to integrate a finding.

Possible decisions:

| Decision | Meaning |
|---|---|
| <text color="success" weight="medium">Accept</text> | The finding is added or integrated into the workspace. |
| <text color="warning" weight="medium">Defer</text> | The finding requires missing information or additional evaluation. |
| <text color="danger" weight="medium">Reject</text> | The finding violates a structural, authorization or integration rule. |
| <text color="info" weight="medium">Merge</text> | The finding is integrated with existing information. |
| <text color="warning" weight="medium">Conflict</text> | The finding is retained for conflict resolution without destroying competing evidence. |

The state manager should create a new workspace revision when accepted changes alter the shared state.

For example:

The actual processing order is not necessarily linear. Several modules may operate simultaneously.

---

### Phase H — Integrate information without losing competing hypotheses

**Step 8. Merge findings according to field-specific rules**

Different cognitive structures need different integration strategies.

| Workspace field | Integration strategy |
|---|---|
| Lexical hypotheses | Maintain candidate sets, confidence, evidence and source |
| Syntactic hypotheses | Maintain competing parse structures |
| Semantic hypotheses | Maintain competing interpretations |
| Working memory | Maintain activated information and retention priorities |
| Retrieved memories | Merge, deduplicate and rank candidates |
| Discourse context | Integrate accepted discourse updates while preserving context history |
| Unresolved questions | Add, resolve or reprioritize questions |
| Current goal | Update through control decisions and task transitions |

The merge function should not be a universal dictionary-overwrite operation.

Each field should have its own integration policy.

#### Example: lexical hypothesis integration

Suppose two modules or two independent processing paths propose:

The system can preserve both candidates.

A weighted combination can be used when combining compatible evidence, but confidence values should not be blindly averaged or multiplied because their evidence may be correlated.

A possible scoring model:

\[
S(h)=
\sum_{i=1}^{n}w_i e_i(h)
\]

Where:

- \(h\): candidate hypothesis.
- \(e_i(h)\): evidence contribution from source \(i\).
- \(w_i\): reliability or importance of the source.

This produces an evidence score, not necessarily a calibrated probability.

The workspace should retain the underlying evidence so that the interpretation can be reconsidered.

---

### Phase I — Notify dependent modules

**Step 9. Publish change events**

Once an update has been committed, the workspace generates an event.

Example:

The notification system examines the subscription matrix and dispatches the event to eligible modules.

For example:

- Working memory may update the active representation.
- Memory retrieval may search for related experiences.
- Cognitive control may evaluate whether additional processing is necessary.
- Discourse processing may update the current discourse representation.

The event should identify the change, not carry an unrestricted instruction to execute arbitrary code.

---

### Phase J — Re-evaluate dependent processing

**Step 10. Trigger relevant modules**

A module may be activated because:

1. New input was received.
2. A subscribed field changed.
3. An unresolved question requires its capability.
4. Cognitive control explicitly requested its operation.
5. A previous operation was deferred and a required dependency became available.

The module should evaluate whether the notification is relevant before performing expensive processing.

A simple relevance score:

\[
R_m = \sum_{j=1}^{n} a_{mj} \cdot \Delta_j
\]

Where:

- \(R_m\): relevance score for module \(m\).
- \(a_{mj}\): module sensitivity or priority for field \(j\).
- \(\Delta_j\): magnitude or significance of the change in field \(j\).

The module may execute when:

\[
R_m \geq \theta_m
\]

Where \(\theta_m\) is a configurable activation threshold.

<text color="secondary">This is an optional computational optimization, not a biological claim that the brain uses this exact equation.</text>

---

### Phase K — Maintain working memory independently

**Step 11. Allow working memory to maintain the workspace's active cognitive contents**

Working memory should not simply copy the entire shared workspace.

It should selectively maintain information relevant to the current goal.

For example, during processing of:

> The boy opened the door.

Working memory may maintain:

Working memory should be able to:

- Activate information.
- Maintain selected information.
- Update active representations.
- Mark information as less relevant.
- Propose removing information.
- Preserve information required for unresolved processing.

Removal from working memory should not delete the information from other workspace structures or long-term memory.

A conceptual retention score:

\[
P_i =
\alpha G_i +
\beta R_i +
\gamma C_i +
\delta U_i
\]

Where:

- \(G_i\): goal relevance.
- \(R_i\): recency or activation.
- \(C_i\): contextual importance.
- \(U_i\): unresolved-task relevance.

The score can help determine what remains active, but the factors and weights should be configurable.

---

### Phase L — Handle conflicts

**Step 12. Maintain a conflict registry**

When a new finding disagrees with an existing finding, the state manager must not automatically destroy either result.

Instead, it creates a conflict record.

Example:

The cognitive control module may decide to:

- Request additional evidence.
- Ask another module to evaluate the conflict.
- Retrieve related memories.
- Revisit an earlier interpretation.
- Temporarily preserve both interpretations.
- Prioritize one interpretation without deleting the other.

This creates a distinction between **the information stored in the workspace** and **the currently preferred interpretation**.

---

### Phase M — Manage workspace snapshots and history

**Step 13. Preserve workspace revisions**

The state manager should maintain versioned snapshots or reconstructable revisions.

A revision should record:

- Revision number.
- Changes made.
- Accepted finding IDs.
- Change origin.
- Dependencies.
- Timestamp.
- Validation result.

The system should support reading an earlier revision to investigate how a conclusion was reached.

This is particularly important if a module's later result invalidates an earlier interpretation.

<text color="success" weight="medium">The workspace should support reversible reasoning rather than irreversible overwriting.</text>

---

### Phase N — Coordinate task completion

**Step 14. Evaluate whether the workspace satisfies the current goal**

The workspace does not independently decide that a sentence is fully understood.

Cognitive control evaluates the accumulated findings against the goal.

For `understand_sentence`, a possible completion criterion is:

- Sufficient lexical coverage.
- At least one viable syntactic interpretation.
- At least one viable semantic interpretation.
- Required referential or discourse information available, when necessary.
- Critical unresolved questions either resolved or explicitly acknowledged.

For example:

\[
C_{\text{goal}} =
w_L C_L +
w_S C_S +
w_M C_M +
w_D C_D
\]

Where:

- \(C_L\): lexical coverage.
- \(C_S\): syntactic adequacy.
- \(C_M\): semantic adequacy.
- \(C_D\): discourse adequacy.

A goal may be completed when:

\[
C_{\text{goal}} \geq \theta_{\text{goal}}
\]

However, this score should be complemented by explicit requirements. A high overall score must not hide the absence of a critical representation.

The goal controller should support at least these outcomes:

- `completed`
- `completed_with_uncertainty`
- `needs_more_processing`
- `blocked`
- `failed`

### 5.2 Important mathematical and computational operations

| Operation | Mathematical / computational concept | Purpose |
|---|---|---|
| Revision validation | Version comparison | Detect stale findings |
| Merge | Set union, deduplication, custom aggregation | Integrate information without destructive overwrites |
| Subscription | Boolean adjacency matrix | Efficiently identify relevant modules |

| Hypothesis evaluation | Weighted evidence score | Rank interpretations |
| Conflict detection | Contradiction and compatibility checks | Preserve competing interpretations |
| Working memory | Priority and retention scoring | Maintain relevant information |
| Scheduling | Dependency graph and queue prioritization | Organize asynchronous processing |
| Provenance | Directed dependency graph | Trace how a finding was generated |
| Goal evaluation | Constraint satisfaction and scoring | Determine processing completion |

### 5.3 Concurrency and consistency requirements

The shared workspace must be safe when multiple modules publish findings at the same time.

The implementation should include:

1. **Optimistic concurrency control** — modules read a snapshot and publish against its revision.
2. **Atomic commits** — a validated update should either be fully committed or not committed.
3. **Duplicate detection** — repeated event delivery should not produce duplicate findings or destructive repeated changes.
4. **Deterministic integration** — equivalent compatible findings should yield reproducible state when processed under equivalent conditions.
5. **Stale finding handling** — revalidate or defer findings when their dependencies have changed.
6. **Event delivery isolation** — a failure in one subscriber should not prevent other subscribers from receiving events.
7. **Bounded processing** — prevent endless module activation loops.
8. **Cancellation and timeout support** — abandoned processing tasks should not indefinitely occupy resources.
