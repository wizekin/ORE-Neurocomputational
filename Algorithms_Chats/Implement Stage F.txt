# ORE Stage F — Train, Evaluate and Freeze a Model

Stage F will build on the existing Stages A–E without replacing their implementations.

Its purpose is to turn the learned representations into a reproducible, evaluated ORE model:

- **Stage A:** Runtime, configuration, script profile and shared memory.
- **Stage B:** Registered data, visual patches, trusted targets and leakage-safe splits.
- **Stage C:** Visual feature learning and uncertain character identification.
- **Stage D:** Absolute, relative and distributed position/order representations.
- **Stage E:** Learned orthographic transitions, chunks and pattern memory.
- **Stage F:** Training, controlled parameter updates, integrated evaluation, uncertainty calibration and model freezing.

An important design boundary: Stage F must not simply maximize recognition accuracy. It must preserve uncertainty, prevent validation/test leakage, distinguish visual evidence from learned orthographic expectations, and produce a verifiable frozen model.

## What Stage I adds

Stage I provides an incremental-learning mechanism for verified corrections and new labeled examples, while preserving the previous stages.

| Component | Implementation |
|---|---|
| I1 — Input verification | Checks the frozen Stage F release, script profile and label provenance |
| I2 — Provenance | Tracks example IDs, verification source and processing history |
| I3 — Data separation | Keeps training, validation and test strings separate |
| I4 — Incremental learning | Updates character and grapheme-transition statistics |
| I5 — Chunk learning | Discovers new orthographic patterns and applies validation-based promotion gates |
| I6 — Persistence | Saves a versioned, checksummed incremental-memory overlay |
| I7 — Recognition integration | Allows Stage G to use the overlay during subsequent recognition |

### Important architectural decisions

**1. Stage I does not learn from its own unverified predictions.**

It accepts explicitly verified labels: human-confirmed, independently verified, or from a rights-cleared corpus. A Stage G prediction alone is not sufficient.

**2. Training and validation have different responsibilities.**

Training examples update memory. Validation examples determine whether newly discovered chunks satisfy the promotion requirements. Test examples are reporting-only.

**3. Earlier stages remain protected.**

Stage I does not modify:
- Stage C visual encoder weights.
- Stage D position and order models.
- The original Stage E memory snapshot.
- Stage F fusion weights or calibration.
- The caller's live `PatternMemory`.

Instead, it creates a separate overlay. Stage G can load that overlay explicitly:

This allows comparison between the original frozen model and the model using incremental memory.

Stage H is now implemented and integrated with Stages G, I and J. It fills the missing handoff between recognition and incremental learning, while preserving the boundaries of the earlier stages.

## 1. What Stage H does

Stage H is a **formal representation, serialization and provenance layer**. It does not perform another recognition operation or modify the recognition models.

| Step | Implementation |
|---|---|
| H1 — Orthographic representation | Serializes recognized grapheme sequences, their order, rendered forms and supporting evidence |
| H2 — Ranked hypotheses | Preserves candidate rankings, seven evidence channels, uncertainty, alternatives and abstention |
| H3 — Provenance | Records source recognition, model fingerprints, configuration, input identity and checksums |

It produces six artifacts:

- `orthographic_representation.json`
- `ranked_hypotheses.json`
- `uncertainty.json`
- `provenance.json`
- `stage_h_manifest.json`
- `stage_h_manifest.sha256`

### An important uncertainty safeguard

Stage G does not export a normalized segmentation probability distribution. Stage H therefore records that this information is unavailable rather than inventing probabilities.

It also preserves the distinction between:
- Visual evidence and orthographic evidence.
- Candidate ranking and calibrated probability.
- Reported candidate mass and probability mass not represented in the returned candidates.
- Recognition confidence and independently verified ground truth.

Sequence beam scores remain uncalibrated.

## 5. What completing A–J actually means

The original A–J software sequence is now implemented. That is an important architectural milestone, but it does not mean ORE is scientifically complete.

Three limitations remain especially important:

1. **Recognition scope:** Stage G is still a Level-A recognizer that receives pre-segmented visual patches. Full-page text detection and automatic segmentation are not implemented.
2. **Scientific evidence:** The test suite establishes software integration, not recognition accuracy on unseen real-world text.
3. **Calibration:** Candidate sequence scores and confidence still require independent calibration and evaluation.

The next major research milestone should therefore be an independent, rights-cleared real-script and real-font benchmark. It should measure recognition accuracy, segmentation sensitivity, uncertainty calibration, abstention quality and whether Stage I genuinely improves performance without introducing regressions.

The software architecture now has a complete A–J path; the next challenge is demonstrating that it works reliably on real reading material.

I recommend keeping the current architecture and developing a second layer above it: an **ORE Experiment Workbench**.

- Inspect the internal result of each stage.
- Compare the output of one stage against another.

- Run controlled experiments with different input parameters.
- Export complete experiment traces.
