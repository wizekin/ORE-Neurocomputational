# ORE Stages A–J — Orthographic Representation, Recognition, Serialization, Incremental Learning and Acceptance

**Version:** 0.6.0  
**Scope:** A–J  
**Status:** All software stages A–J are implemented as research prototypes; scientific acceptance requires independent rights-cleared real-corpus evaluation and preregistered held-out testing.

The ORE pipeline is built as cooperating stages; each stage extends the previous contracts without replacing them:

- **Stage A:** validated runtime, script profile, deterministic seeds, trace and shared `PatternMemory`.
- **Stage B:** registered samples, Unicode/grapheme metadata, train/validation/test partitions, learning-regime and exposure manifests, prepared patches.
- **Stage C:** learned visual feature vectors and grapheme posterior distributions, including unresolved/unknown identity.
- **Stage D:** physical/logical position, absolute-slot (A), relative/open-bigram (B), distributed-overlap (O) and hybrid representations.
- **Stage E:** soft transition statistics, local skip-pair statistics, chunk-candidate discovery, held-out MDL-style evaluation and auditable pattern-memory updates.
- **Stage F:** trainable evidence fusion across C/D/E, paired-view consistency, pairwise-order calibration, masked-character prediction, validation/ablations, uncertainty calibration and frozen release.
- **Stage G:** read-only recognition from supplied visual patches; script-aware ordering; multiple segmentation hypotheses; seven evidence channels; bounded sequence decoding; alternatives and abstention.
- **Stage H:** canonical serialization of the Stage G orthographic representation, ranked hypotheses, uncertainty, and complete provenance; exposes a verified-feedback adapter for Stage I.
- **Stage I:** opt-in incremental learning from explicitly verified grapheme sequences; train-only memory deltas; validation-gated chunk promotion; checksummed overlay that Stage G can load without changing the frozen Stage F release; records Stage H provenance when feedback originates from an H bundle.
- **Stage J:** package integrity, runtime/import checks, complete regression execution, scientific-evidence separation, acceptance reports, and release archive validation.

## Main integration APIs

Stage E learns patterns from A/B/D evidence:

```python
from ore_stage_e import StageEConfig, train_stage_e

stage_e = train_stage_e(
    context,       # OREContext from Stage A
    stage_b,       # StageBResult from Stage B
    stage_d,       # StageDResult from Stage D, carrying C/A/B/O channels
    config=StageEConfig(),
)
```

Stage F trains the integrated fusion model and freezes the release bundle:

```python
from ore_stage_f import StageFConfig, train_stage_f, load_stage_f_model

stage_f = train_stage_f(
    context,
    stage_b,
    stage_c,
    stage_d,
    stage_e,
    config=StageFConfig(),
)
frozen_model = load_stage_f_model(
    stage_f.output_directory,
    expected_script_profile_fingerprint=context.script_profile.fingerprint,
)
```

Stage F validates the Stage A–E run IDs, script-profile fingerprints, persisted upstream artifacts, training exposure memory, patch coverage and all learning-eligibility flags before training. It trains only its fusion parameters and a two-parameter calibrator over Stage D's pairwise order probabilities; Stage C's visual encoder, Stage D's position/order backends and Stage E's memory remain unchanged.

## E1–E5 implementation notes

### E1 — Soft transition and local-pair statistics

- Learns conditional grapheme transitions from unigram through the configured context order.
- Retains both adjacent transitions and configurable local pairs with intervening-grapheme counts.
- For labeled samples, normalized Stage B text exposures provide trusted grapheme sequences.
- For unlabeled samples, Stage D candidate probability distributions contribute fractional expected counts. The engine does not turn a top-1 prediction into a trusted label.
- `<UNK>` probability is retained in transition and character statistics.
- Lifetime and decaying recent counts remain separate. Recent decay is applied once per newly processed training exposure; lifetime counts are never decayed.
- Prediction uses additive smoothing and longest-context suffix backoff.

### E2 — Chunk candidate discovery

- Enumerates contiguous grapheme sequences between length 2 and configured `max_chunk_length`.
- Candidate support for soft input is an expected probability mass, not an integer occurrence count.
- Candidate expansion is bounded by top-k candidates per position and a maximum number of combinations per span.
- Candidate symbols must belong to the script profile. Unknown probability is preserved but cannot create a named chunk.
- Context diversity, distinct trusted strings, relative position buckets and source exposure IDs are retained.
- Complete training strings are not treated as sublexical chunks by default. Whole-string candidates require explicit opt-in.

### E3 — Baseline versus chunk coding

- Compares an independent-grapheme baseline against a candidate chunk using an MDL-style expected coding-cost estimate.
- Candidate code length uses smoothed support; complexity cost is charged by chunk length.
- Candidate promotion depends on validation gain, not test gain.
- Exact normalized grapheme-sequence overlap among train/validation/test is independently rejected in `string_generalization` mode.
- This is a transparent MDL-style approximation, not a complete joint minimum-description-length optimizer: candidates are evaluated independently and overlapping candidates can make aggregate gains non-additive. The report marks this limitation explicitly.

### E4 — Candidate promotion

A candidate is promoted only when all configured criteria pass:

1. minimum expected training support;
2. enough distinct trusted training strings;
3. sufficient left-context diversity;
4. sufficient right-context diversity;
5. sufficient held-out validation MDL-style gain after complexity cost;
6. string-generalization split, by default.

Test performance is recorded for reporting only and never changes promotion status.

### E5 — Memory maintenance

- Stores candidate records in Stage A's shared `PatternMemory` under a Stage E namespace.
- Records promotion/demotion, update index, config fingerprint and processed exposure IDs.
- Training exposure processing is idempotent.
- Lifetime and recent counts are persisted separately.
- Memory is computed on a deep copy and committed to the live context only after output artifacts are successfully written.
- A SHA-256-verified memory snapshot can be loaded with `load_stage_e_pattern_memory()`.

## Important limitations

- Stage E consumes Stage D sequence representations and Stage B grapheme exposures; it does not read raw page images or perform segmentation.
- It is a statistical orthographic-learning baseline, not a full reading system or a biological simulation.
- Chunk support for unlabeled input is probabilistic expected mass. It cannot create trusted distinct-string evidence and therefore cannot satisfy promotion diversity on its own.
- The MDL-style cost calculation is not a jointly optimized code over overlapping chunks. Independent candidate comparisons are useful diagnostics, but a future Stage F experiment should compare joint segmentation/lexicon optimizers.
- Chunk promotion is deliberately conservative and defaults to string-generalization validation. Real-corpus behavior remains unproven.
- Arabic/RTL and other scripts depend on correct Stage A/B grapheme inventories and Stage B logical-order preparation. Multi-codepoint graphemes are compared as tuples, not by ambiguous rendered-string concatenation.

## F1–F6 implementation notes

### F1 — Composite training objectives

Stage F builds seven per-candidate evidence channels:

1. Stage C visual posterior log probability.
2. Stage C prototype-similarity log probability.
3. Stage D absolute-position channel A.
4. Stage D relative/open-bigram channel B.
5. Stage D distributed-overlap channel O.
6. Stage E transition-prior log probability.
7. Stage E promoted-chunk completion evidence.

The prior channels are computed over a bounded beam of uncertain visual-prefix hypotheses rather than a single top-1 prefix. Stage D's pair activations already include the first-character posterior; Stage F converts them to conditional pair evidence before marginalizing over the beam so the first-character mass is not double-counted.

The trainable fusion head uses a weighted objective:

`L = λid Lid + λview Lview + λord Lord + λmask Lmask + λreg Lreg`

- `Lid`: cross-entropy over trusted Stage B identity labels.
- `Lview`: squared difference between character posterior distributions for original and augmented training views.
- `Lord`: binary cross-entropy over Stage D pair-order probabilities, with reverse pair directions as explicit negatives.
- `Lmask`: next-grapheme cross-entropy using training-only masked exposures and Stage E transition/chunk priors.
- `Lreg`: L2 penalty over fusion and order-calibration parameters.

Every component and weight is logged independently. A component with no eligible training examples contributes zero and is visible in the history. Stage E's chunk MDL promotion remains its separate discrete procedure; Stage F does not pretend that the Stage E independent-candidate MDL estimate is a globally optimized segmentation objective.

### F2 — Parameter updates

- Full-batch Adam updates train only the Stage F class-by-channel fusion weights, class biases and two order-calibration parameters.
- A configured global gradient-norm clip is applied across all trainable parameters.
- Update count and Adam first/second moments are persisted in `optimizer_state.npz`.
- No validation or test example contributes to gradient updates.
- The initial visual channel is the only active fusion channel at initialization; other channels begin neutral so an orthographic prior cannot dominate visual evidence before training.

### F3 — Pattern-memory handoff

Stage E has already processed the Stage B training-eligible exposures before Stage F begins. Stage F independently verifies that every expected labeled or unlabeled training exposure is present in Stage E's processed-exposure ledger, verifies the memory update index and checksum, then pins a copy into the Stage F release. It deliberately does not call Stage E again, which would be redundant and could obscure exposure accounting. Validation/test exposures remain evaluation-only and are not committed to the memory.

### F4 — Validation and ablations

- The fusion head is evaluated on train, validation and test identity targets; validation/test never update parameters.
- Reports include top-1/top-3 accuracy, NLL, Brier score, ECE, visual-only accuracy, prior-assisted rescue rate, false-correction rate and unknown posterior mass.
- Pairwise order metrics are reported separately.
- Seven one-channel-at-a-time ablations are run on validation and test splits.
- Early stopping and best-epoch selection use validation NLL only; test metrics are reporting-only.

### F5 — Confidence calibration and abstention

- Temperature scaling is fitted only on validation labels when the configured minimum sample count is met.
- A confidence threshold is selected on the calibrated validation predictions to maximize coverage subject to the preregistered target selective risk.
- Brier score and ECE are reported for each identity split.
- When validation evidence is insufficient, Stage F marks the model `UNCALIBRATED_INSUFFICIENT_VALIDATION_LABELS` and leaves the abstention threshold unset. It does not borrow test labels to repair calibration.

### F6 — Frozen release

Stage F writes under `data/stage_f/<stage_f_id>/`:

- `fusion_weights.npz` — learned fusion and order-calibration parameters.
- `optimizer_state.npz` — final Adam moments and update count.
- `model_metadata.json` — stage IDs, script profile, config, channel contract and provenance.
- `training_history.json`, `evaluation.json`, `ablation_report.json`, `calibration.json`.
- `pattern_memory.json` and `pattern_memory_audit.json` — verified Stage E memory snapshot and training-exposure audit.
- `upstream/` — checksummed copies of the Stage C encoder/prototypes/clusters, Stage D order backend and Stage E memory.
- `stage_f_manifest.json` — split hash, checkpoint hash, per-artifact SHA-256 inventory and frozen status.

`load_stage_f_model()` checks schema/profile compatibility, all release artifact hashes, model tensor shapes, calibration consistency and the memory audit. Loaded NumPy parameter arrays are write-protected. `LoadedStageFModel.score()` returns per-class, per-channel contributions; `calibrate_order_probability()` applies the fitted pairwise-order calibrator.

## Current development boundary and limitations

Stages A–F are implemented as software prototypes. Stage F is an evidence-fusion head, not an end-to-end fine-tuned visual encoder: upstream C and D weights are intentionally frozen so attribution and regression analysis remain possible. Its linear fusion and bounded visual-prefix beam are controlled baselines, not proof of a biologically faithful computation. Stage E's MDL approximation still does not jointly optimize overlapping chunks and sequence segmentation. The synthetic demonstration verifies integration only. Independent rights-cleared real-font/script benchmarks, controlled minimal pairs, held-out font/string recombination, multi-seed comparisons, and external calibration analysis remain necessary before scientific acceptance or claims of human-like reading performance.


## Stage G — recognize a new visual string

Stage G loads and verifies the frozen Stage F release, accepts a flat patch list or multiple weighted `SegmentationHypothesis` alternatives, obtains Stage C character distributions, reconstructs Stage D position/order channels, activates Stage E chunk/transition knowledge and applies Stage F's evidence-fusion head. It returns ranked grapheme-sequence hypotheses with visual likelihood and each orthographic evidence contribution separately inspectable.

```python
from ore_stage_g import StageGConfig, SegmentationHypothesis, recognize_stage_g

result = recognize_stage_g(
    context,
    stage_f.output_directory,
    (SegmentationHypothesis("candidate-segmentation", tuple(visual_patches)),),
    config=StageGConfig(beam_width=64, top_k=5),
)
print(result.status, [candidate.rendered for candidate in result.top_candidates])
```

Stage G is read-only and never updates the frozen model or Stage E memory. It supports pre-segmented Level-A patches, not full-page OCR. Sequence beam probabilities are not calibrated sequence confidence; low evidence, weak segmentation or insufficient separation can produce `ABSTAIN`. See `STAGE_G_IMPLEMENTATION_REPORT.md` for algorithm coverage, verification and limitations.

Run the complete synthetic integration path with `python examples/run_stage_g_demo.py`. The generated glyph fixtures verify software integration only, not OCR accuracy.



## Stage H — serialize orthographic representations and provenance

Stage H is the stable interchange boundary after Stage G. It consumes the persisted Stage G `recognition_result.json` and `recognition_manifest.json`, validates that their IDs, parent model, input fingerprint and read-only declarations agree, then writes a versioned JSON bundle. It does not perform recognition again or modify any model.

```python
from ore_stage_h import StageHConfig, serialize_stage_h, load_stage_h_bundle

stage_h = serialize_stage_h(stage_g_result, config=StageHConfig())
bundle = load_stage_h_bundle(stage_h.output_directory)
ranked = bundle["ranked_hypotheses.json"]["candidates"]
print([(row["rank"], row["rendered"]) for row in ranked])
```

The bundle contains `orthographic_representation.json`, `ranked_hypotheses.json`, `uncertainty.json`, `provenance.json`, `stage_h_manifest.json`, and a manifest checksum sidecar. It preserves grapheme arrays, the seven Stage F evidence contributions, visual/character uncertainty, order evidence, segmentation support, Stage G abstention, and lineage from the input through the frozen Stage F checkpoint.

Sequence beam mass remains uncalibrated. Stage H records the returned candidate mass and unreported mass, and calculates entropy only conditionally on the returned candidate set. Stage G does not currently export a normalized segmentation posterior, so Stage H explicitly marks that distribution unavailable rather than synthesizing it.

To pass a later independently verified correction into Stage I, use `make_stage_i_feedback_example()`. You must provide the verified grapheme tuple and verification provenance; the adapter never copies a Stage G prediction into a training label automatically. The resulting Stage I example records the Stage G recognition ID, Stage H ID, and Stage H bundle SHA-256:

```python
from ore_stage_h import make_stage_i_feedback_example

verified_example = make_stage_i_feedback_example(
    stage_h.output_directory,
    example_id="correction-001",
    graphemes=("c", "a", "b", "d"),  # independently verified label
    split="train",
    verification_status="HUMAN_CONFIRMED",
    source_id="reviewed-corrections-v1",
    verification_reference="review-record-001",
)
# Include this in learn_stage_i() with its separate held-out validation examples.
```

## Stage I — incremental learning from verified feedback

Stage I is a controlled adaptation layer for labels arriving after Stage F has been frozen. It rejects unverified model guesses as training labels. Examples produced by Stage H can carry a Stage H bundle ID and SHA-256 fingerprint into the Stage I provenance ledger; legacy examples without Stage H linkage remain supported. Callers must supply explicitly verified grapheme sequences and assign them to train, validation or test partitions. Exact string overlap across partitions is rejected by default.

```python
from ore_stage_i import IncrementalExample, StageIConfig, learn_stage_i

feedback = (
    IncrementalExample("correction-001", ("c", "a", "b", "d"), "train",
        "HUMAN_CONFIRMED", "reviewed-corrections-v1", "review-record-001",
        recognition_id="ore-stage-g-previous-result"),
    IncrementalExample("correction-002", ("e", "a", "b", "f"), "train",
        "HUMAN_CONFIRMED", "reviewed-corrections-v1", "review-record-002"),
    IncrementalExample("correction-003", ("g", "a", "b", "h"), "train",
        "HUMAN_CONFIRMED", "reviewed-corrections-v1", "review-record-003"),
    IncrementalExample("validation-001", ("i", "a", "b", "j"), "validation",
        "INDEPENDENTLY_VERIFIED", "reviewed-validation-v1", "validation-record-001"),
)

stage_i = learn_stage_i(
    context, stage_f.output_directory, feedback, config=StageIConfig()
)
```

Use the overlay explicitly when recognizing new patches:

```python
result = recognize_stage_g(
    context, stage_f.output_directory, segmentation_hypotheses,
    incremental_memory_directory=stage_i.output_directory,
)
```

Only `train` examples update character/transition memory. Validation examples are used for chunk-promotion gates; test examples are reporting-only. Stage I does not fine-tune Stage C, D or F and does not mutate the caller's live PatternMemory. The overlay is pinned to the exact frozen Stage F parent and checked by SHA-256 before Stage G uses it. See `STAGE_I_IMPLEMENTATION_REPORT.md` for equations, steps, verification and limitations.

The Stage I evidence-strength heuristic is not a calibrated probability or the MDL score used by Stage E. Real-corpus adaptation benefit, forgetting and calibration drift remain untested.


## Stage J — software acceptance and release gating

Stage J is the acceptance layer around the implemented pipeline. It checks the complete A–J scope, verifies every manifest-pinned file and the package-manifest checksum, checks Python/dependency compatibility, imports the stage modules in a fresh process, runs the complete regression suite, records evidence, and creates a validated ZIP release when all software gates pass.

Stage J does **not** treat successful software tests as scientific validation. The scientific gate remains separate and cannot be auto-approved. A structured evidence file can be marked `READY_FOR_INDEPENDENT_REVIEW`, but Stage J never emits `SCIENTIFICALLY_ACCEPTED`. Stage J requires all ten stages and their dedicated tests, including Stage H, before accepting the software sequence.

Run Stage J from the package directory:

```bash
python ore_stage_j.py . --output ../ore_stage_j_acceptance --archive ../ORE_Stages_A_to_J_v0.6.0.zip
```

Run checks without building an archive:

```bash
python ore_stage_j.py . --no-archive
```

Skipping the regression tests (`--no-tests`) is diagnostic only and blocks software acceptance. See `STAGE_J_IMPLEMENTATION_REPORT.md` for the J1–J9 acceptance algorithm, evidence contract, public API, and limitations.
