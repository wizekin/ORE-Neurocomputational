# ORE–USG integration review

The two repositories have complementary responsibilities that make integration worthwhile.

- **ORE-Neurocomputational** should remain the cognitive processing and coordination architecture: it processes inputs, coordinates specialized modules, maintains memory, handles uncertainty, and performs controlled learning.
- **USG-Workbench** can provide a structured language and knowledge layer: lexical resources, grammatical information, predicate frames, semantic graphs, contextual relations, evidence, and interpretation alternatives.

I recommend building **an ORE-native USG adapter layer**, rather than importing the entire USG Workbench into ORE. That would let ORE use USG resources while retaining its own module interfaces, execution coordinator, memory, learning policies, and SQLite logging.

An important distinction: USG's valid semantic structures are not automatically correct interpretations, and its candidate resources must not automatically become trusted ORE knowledge.

## 1. What each repository already contributes

### ORE-Neurocomputational

ORE is much more than the visual-processing pipeline described in its original README. Its current repository contains a substantial collection of separate cognitive systems:

| ORE subsystem | Existing responsibility |
|---|---|
| N1–N4 | Visual processing, orthographic representations, prediction and attention |
| N5–N6 | Experience-dependent learning and lexical access |
| N9 | Integrated recognition and language-processing controller |
| Semantic cognition | Concept representations, distributed semantic features and semantic composition |
| Language processing | Lexical context, syntax, discourse, comprehension and interpretation |
| Knowledge and memory | Prior knowledge, working memory, episodic memory, schema formation and analogical transfer |
| Integration | Module registry, contracts, dependency planning, resource allocation and logging |

The important discovery is that ORE already has several integration mechanisms that we should reuse.

**A. Its module communication architecture**

The `ore_contracts` package provides:

- `ModuleManifest`, `InputPort` and `OutputPort` for describing modules.
- `ModuleRegistry` for registering modules and binding executable backends.
- `ContractArtifact` and `ContractEnvelope` for exchanging typed, hashed and provenance-tracked information.
- `ContractCatalog` for validating exact contract versions.
- `CognitiveTaskCoordinator` for planning dependent module execution.

This is an excellent foundation for introducing USG as a group of optional ORE resources and capabilities.

See [ORE module manifests](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_contracts/module_manifest.py), [artifacts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_contracts/module_artifacts.py) and [coordinator](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_contracts/coordinator.py).

**B. The new adaptive resource coordinator**

ORE's latest main commit, `55105d65` from November 20, merges PR #82, *Teach ORE to coordinate its cognitive resources*.

It introduces:

- `TaskProfileRegistry`
- `AdaptiveResourceCoordinator`
- `ModuleResourceEstimator`
- `InformationGainEstimator`
- `ModuleReliabilityTracker`
- `ResourceScorer`
- `SQLiteResourceHistory`

This is particularly relevant. We can register USG capabilities as resources that ORE calls when a task requires them, rather than loading every USG capability into every processing request.

[ORE Task 07 merge](https://github.com/wizekin/ORE-Neurocomputational/commit/55105d6514dfdff64b72753072c69a1fac51701b) · [Resource coordination implementation](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_contracts/resource_coordination.py).

**C. The existing N9 language interfaces**

ORE's N9 controller already has injectable interfaces for:

- N6 lexical access
- Syntax processing
- N7 context and discourse
- N8 semantic composition

It does not need another complete language-processing pipeline. We can supply USG resources through those existing interfaces.

In particular, ORE already has an end-to-end test that connects lexical access, syntax, semantic composition and discourse through N9.

See [N9 architecture](https://github.com/wizekin/ORE-Neurocomputational/blob/main/docs/N9_ARCHITECTURE.md), [N9 adapter contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_n9/contracts.py) and [existing language integration tests](https://github.com/wizekin/ORE-Neurocomputational/blob/main/tests/test_n9_language_adapters.py).

One architectural distinction matters here: the existing `ore_n9` processing package and the newer canonical B-N9 controller are not interchangeable. We should register new USG capabilities through the canonical module registry, and expose suitable adapters to the existing `ore_n9` interfaces where necessary.

### USG-Workbench

USG contributes a different set of capabilities.

| USG subsystem | What it can provide to ORE |
|---|---|
| USG-SEM/1.0 | Canonical, structured semantic documents |
| USG-KNOWLEDGE/0.1.0 | Typed lexical, conceptual and knowledge records |
| Lexical resources | Word forms, lemmas, senses, POS and morphological information |
| Semantic frames | Predicate definitions, argument roles and filler constraints |
| Interpretation pipelines | Lexical, syntactic, compositional and discourse interpretation candidates |
| Knowledge retrieval | Context-sensitive retrieval of records, concepts and relations |
| Provenance system | Source identities, evidence, derivation and resource versions |
| Phase 8 | A system-wide inventory of resources, evaluation results and development evidence |

USG's most valuable contribution is not simply its interpreter. It is the combination of **structured semantic information, versioned resources, explicit ambiguity, and evidence provenance**.

Its documented processing architecture preserves information through lexical, syntactic, semantic and discourse stages rather than pretending that every input has one certain interpretation.

See [USG architecture](https://github.com/wizekin/USG-Workbench/blob/main/README.md), [interoperability documentation](https://github.com/wizekin/USG-Workbench/blob/main/interoperability/README.md) and [USG-SEM/1.0](https://github.com/wizekin/USG-Workbench/blob/main/specifications/USG-SEM-1.0.md).

This is the most important part of the review. We should not create one massive adapter. We should create several specialized adapters, each connecting a specific USG resource to the ORE structure that can use it.

This is the best starting point because ORE already accepts externally supplied lexical inventories. Its syntax processor also accepts lexical entries and token-specific POS evidence.

USG provides information ORE currently needs without requiring us to rewrite ORE's lexical algorithm.

The USG English starter lexicon `resources/lexical/v0.5.0` is a useful initial source, although it explicitly identifies itself as a bounded starter lexicon rather than a complete dictionary. The bilingual knowledge resources are a more promising longer-term source.

References: [USG English lexical resource](https://github.com/wizekin/USG-Workbench/blob/main/resources/lexical/v0.5.0/en-core-starter-lexicon.json), [ORE lexical contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_lexical_context/contracts.py).

<badge color="success">Highest priority</badge> **Adapter 2 — USG semantic concepts → ORE semantic representations**

USG distinguishes several things that ORE needs to keep separate:

- A surface word form.
- A lemma.
- A lexical sense.
- An abstract concept.
- A semantic class.
- A mapping between senses and concepts.

This distinction can improve ORE's concept resolution.

For example, one word can have two different senses that refer to different concepts. The adapter must not collapse them merely because their spelling is identical.

The destination should include:

- `ore_semantic.SemanticConcept`
- `ore_semantic_composition.SemanticCompositionProcessor`
- `ore_atl_amodal.AmodalConcept`
- `ore_hub_spoke` and `ore_distributed_semantics`

There is one important technical limitation: ORE semantic features are numeric activation values in the interval `[0, 1]`. USG lexical and concept records frequently contain symbolic information, definitions and identifiers instead.

We must not invent numerical feature vectors from definitions or POS tags. The adapter should preserve the symbolic information and populate numeric feature maps only when a legitimate source or separately documented feature-extraction method supplies them.

References: [ORE semantic contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_semantic/contracts.py), [USG knowledge specification](https://github.com/wizekin/USG-Workbench/blob/main/specifications/USG-KNOWLEDGE-0.1.0.md).

**Adapter 3 — USG predicate frames → ORE semantic composition**

This may eventually be one of the most powerful integrations.

USG predicate frames describe how events and states are structured, including roles such as:

- Agent
- Patient
- Theme
- Recipient
- Experiencer
- Instrument
- Location
- Cause
- Time

ORE's `PredicateFrame` already accepts predicate identities, participant roles, required roles and selectional preferences.

The adapter can convert compatible USG frames into ORE predicate frames. That would enrich ORE's ability to construct sentence-level propositions rather than merely identify individual word meanings.

However, the two representations are not identical. USG frames can contain constraints such as minimum and maximum filler counts, permitted filler sorts, and evidence policies. ORE's existing frame contract does not represent all of those fields.

Therefore, the adapter must preserve the complete USG frame separately and only project it into ORE's simpler frame representation when the mapping is safe. Otherwise, the frame should remain available as structured evidence without being used as an executable ORE frame.

There is another important restriction: the USG semantic-frame registry identifies its frame records as `CANDIDATE`. They should not become automatically trusted ORE rules.

References: [USG semantic-frame registry](https://github.com/wizekin/USG-Workbench/blob/main/resources/semantic-frames/v0.3.0/registry.json), [ORE semantic composition contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_semantic_composition/contracts.py).

**Adapter 4 — USG semantic documents → ORE semantic artifacts**

USG-SEM/1.0 can carry considerably richer information than a simple sentence representation.

It includes structured representations of:

- Sources and source references.
- Referents and mentions.
- Expressions and assertions.
- Predicate structures.
- Evidence and contexts.
- Derivations.
- Unresolved items.
- Mapping coverage and validation results.

I recommend an adapter that imports the complete USG document into an immutable ORE artifact.

ORE can then project supported parts into its own semantic representations while retaining the original USG document and identifying anything it cannot represent.

This is especially important because ORE's existing N8 semantic adapter is intentionally conservative: it can supply concept nodes, but it does not manufacture predicate relations or other semantic facts.

We should not reduce a rich USG document to those concept nodes and silently discard the rest.

References: [USG-SEM/1.0 specification](https://github.com/wizekin/USG-Workbench/blob/main/specifications/USG-SEM-1.0.md), [ORE N9 adapters](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_n9/adapters.py).

**Adapter 5 — USG discourse and context → ORE discourse systems**

USG's referents, mentions, discourse relations, contextual evidence and unresolved references can supply information to:

- `ore_discourse.DiscourseProcessor`
- `ore_context_dependent_interpretation`
- `ore_language_comprehension`
- `ore_working_memory`
- `ore_schema_guided_inference`

For example, USG can provide an explicit reference candidate and its supporting evidence. ORE can use that information when constructing a situation model.

But an unresolved USG reference must remain unresolved in ORE. A mention is not automatically an identified real-world entity.

References: [ORE discourse contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_discourse/contracts.py), [ORE context interpretation contracts](https://github.com/wizekin/ORE-Neurocomputational/blob/main/ore_context_dependent_interpretation/contracts.py).

**Adapter 6 — USG knowledge retrieval → ORE memory and prior knowledge**

USG Phase 7 provides typed relations, concepts, source reconciliation, contextual retrieval and read-only knowledge adapters.

This can give ORE a more structured knowledge source.

The most suitable destinations are:

- `ore_prior_knowledge`
- `ore_memory_integration`
- `ore_context_dependent_interpretation`
- `ore_schema_guided_inference`
- `ore_workspace`

I recommend a read-only knowledge provider initially. ORE should request relevant knowledge when a task requires it, rather than importing the complete USG knowledge repository into its active memory.

Do not share the two projects' SQLite databases. USG's knowledge repository has its own persistence and transaction ownership. Exchange versioned knowledge bundles or use a defined read-only API instead.

Reference: [USG Phase 7 knowledge read adapter](https://github.com/wizekin/USG-Workbench/blob/main/tools/phase7_knowledge_integration/read_adapter.py).

## 3. Important findings that affect the design

### A. USG's accepted status is bounded

USG Phase 7 is documented as accepted for its frozen English/MSA Arabic profile.

Its recorded acceptance includes 46/46 exact-form positive retrieval cases, 46/46 wrong-language negative cases, 10/10 OOV negative cases and 2/2 polysemy cases. Importantly, all 43 cross-language mapping proposals remained unresolved.

That is useful evidence: USG is already designed to preserve ambiguity and prevent unsupported mappings.

But the acceptance record explicitly does not claim unrestricted semantic understanding or general semantic truth.

[Phase 7 completion record](https://github.com/wizekin/USG-Workbench/blob/main/documentation/PHASE-7-COMPLETION-RECORD.md).

### B. The implementations within USG are not fully interchangeable

The USG cross-implementation matrix, updated November 16, reports that shared cross-runtime conformance has not yet been established.

The JavaScript Workbench, Python reference kernel and Python interpretation pipelines have different implementation boundaries and capabilities.

Consequently, I would make ORE consume the canonical USG specifications and explicitly versioned resources—not depend on an assumption that all USG implementations produce equivalent interpretations.

[USG cross-implementation matrix](https://github.com/wizekin/USG-Workbench/blob/main/documentation/USG-CROSS-IMPLEMENTATION-CONFORMANCE-MATRIX.md).

### C. Keep evidence status separate from knowledge acceptance

USG distinguishes resource states such as:

`CANDIDATE`, `VALIDATED_FOR_PROFILE`, `ACCEPTED`, `DEPRECATED`, `REJECTED` and `UNRESOLVED`.

These states should be preserved in ORE.

In particular, `ACCEPTED` means accepted within a declared USG resource scope. It must not automatically mean that every proposition involving that resource is a verified fact.

Likewise, a retrieval ranking score must not be converted into a probability of truth.

ORE's existing memory contracts already distinguish relevance, confidence, verification status and provenance. We should retain those distinctions.

### D. Licensing is manageable

ORE is MIT-licensed and USG is Apache-2.0-licensed. These licenses permit a workable integration, with the relevant Apache license, modification notices and other required attribution retained when USG code is reused.

However, the source rights for individual knowledge records and external lexical resources must still be respected. A repository-wide code license does not automatically grant redistribution rights for every piece of data in the repository.

[ORE license](https://github.com/wizekin/ORE-Neurocomputational/blob/main/LICENSE) · [USG license](https://github.com/wizekin/USG-Workbench/blob/main/LICENSE).

## 5. Implementation order

I recommend the following sequence.

| Priority | Implementation | Expected benefit |
|---:|---|---|
| 1 | USG knowledge and lexical adapters | Expands ORE's lexical and morphological resources |
| 2 | Concept and semantic-class adapters | Improves semantic representations and concept selection |
| 3 | Predicate-frame adapter | Adds richer predicate-argument structures |
| 4 | Semantic-document adapter | Preserves complete structured interpretations |
| 5 | Discourse and contextual adapters | Improves references and situation models |
| 6 | Knowledge retrieval and memory integration | Connects external structured knowledge with ORE memory |
| 7 | N9 and adaptive coordination integration | Makes the capabilities available when appropriate |
| 8 | Evaluation and cross-system feedback | Identifies weaknesses and measures actual improvement |

### The first implementation should be deliberately small

I would make the first PR contain:

1. The `ore_usg` package foundation.
2. Validation of `USG-KNOWLEDGE/0.1.0` records and version metadata.
3. A read-only lexical adapter producing ORE `LexicalEntry` and `LexicalMeaning` records.
4. Provenance and lifecycle-state preservation.
5. Module registration through `ore_contracts`.
6. Tests proving that multiple senses, languages and source identities survive conversion.

I would initially use namespaced contracts such as `ORE.USG.KNOWLEDGE_BUNDLE` and `ORE.USG.SEMANTIC_DOCUMENT`, registered through ORE's existing `ContractCatalog`. We should not introduce new `IF-*` numbers without first reviewing the existing interface registry.

For logging, ORE's AST-backed annotation catalog can store the new classes, functions and methods in SQLite. One detail to address is that `register_module_annotations()` currently indexes `ore_contracts`; we should extend its registration scope to include `ore_usg`, and record adapter executions through the existing SQLite event logger.

Testing should include preservation of Arabic and English text, Unicode source offsets, ambiguous senses, unresolved references, incompatible versions, unsupported mappings and rights restrictions. Importing a valid JSON document must never silently turn unsupported semantics into invented ORE facts.

I did not modify either repository or execute their test suites during this review. For the implementation, I recommend local-first validation, fixing and rerunning tests before pushing changes.

## 2. Important safeguards

The implementation preserves several distinctions that are important for ORE's future reasoning capabilities.

**Polysemy:** Multiple meanings of the same lemma remain separate. The adapter does not select one meaning prematurely.

**Knowledge lifecycle:** Only `ACCEPTED` and `VALIDATED_FOR_PROFILE` records are imported by default. Candidate records require explicit opt-in.

**Source rights:** Records with unknown, restricted or prohibited local-use rights are excluded.

**Contradictory evidence:** Supporting and contradicting evidence remains separately accessible in the import report. The adapter does not resolve disagreements.

**Context:** Language and domain context records are preserved.

**Provenance:** Original USG record IDs, evidence references, source references and bundle fingerprints remain available.

**Identifier collisions:** ORE lexical IDs are namespaced using the USG namespace and bundle identity, preventing collisions between independent knowledge bundles.

**No fabricated semantics:** Definitions become glosses. The adapter does not manufacture numeric semantic feature vectors or infer missing morphological relationships.

# ORE–USG Integration Roadmap

The first step—**a read-only USG knowledge-to-ORE lexical adapter**—has been implemented on the feature branch. The following is the proposed sequence for completing the integration, without starting implementation yet.

## Phase 1 — Establish the integration foundation

1. **Verify the lexical adapter**
   - Run its focused tests locally.
   - Check compatibility with the current ORE and USG contracts.
   - Resolve any failures before merging.

2. **Establish a shared USG-to-ORE adapter framework**
   - Define common import, validation, provenance, and error-handling conventions.
   - Standardize how adapters identify USG records and ORE resources.
   - Preserve read-only behavior and source traceability.

3. **Add USG bundle discovery and loading**
   - Identify how ORE can receive exported USG knowledge bundles.
   - Support loading bundles from files or an explicitly supplied data source.
   - Verify bundle versions, fingerprints, and integrity.
   - Keep database access outside the adapters initially.
